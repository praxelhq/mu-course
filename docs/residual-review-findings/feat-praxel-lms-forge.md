The Unlock Console's single-cell toggle lets an instructor set just the session row to 'closed' (bulkClose is a separate button) — then every in-flight quiz taker gets available:false with ownState 'open', inGrace false, and submitQuizAttempt returns 'not_available' (rendered as a 404-ish dead end, not even 'closed'). Students who had the form open lose their answers instantly with zero grace, defeating exactly the mid-class-close scenario GRACE_SECONDS exists for, and the draft-count confirm guard also doesn't apply to session-level closes.
  - Fix: Extend GateDecision with the parent gate's closedAt and accept grace when EITHER the own gate or the parent session gate closed within GRACE_SECONDS: `const inGrace = [own, parent].some(g => g?.state === 'closed' && g.closedAt && now - g.closedAt <= GRACE_SECONDS*1000)`. resolveGateDetail already selects closedAt for the own row; add it for the parent row.
  - Reviewers: adversarial; confidence 75; validated true.
- **[P2] #28** `lms/lib/submissions.ts:262` — Double-submit races allocate duplicate submission versions and double grading cost
  - Why: submitAssignment computes version as max+1 via a read inside an interactive transaction, but READ COMMITTED gives no serialization and the schema has only a non-unique index on (assignmentId, userId, version) — two clicks of the submit button race to two rows both stamped v2. Each row independently enqueues a grading job, so one double-click burns two full model calls, produces two Grade rows and two notifications, and leaves 'latest version' resolution hanging on a createdAt tiebreak. The quiz submit path in the same codebase solves this exact shape with a unique constraint and P2002 catch — the assignment path skipped it.
  - Fix: Promote the index to a constraint: `@@unique([assignmentId, userId, version])`, and wrap the create in a P2002 retry that re-reads max version (bounded retries, mirroring appendTurn in lib/interview/session.ts:334). Additionally short-circuit when the latest submission has an identical contentHash created within a few seconds.
  - Reviewers: adversarial; confidence 75; validated true.
- **[P2] #29** `lms/worker/jobs/grade-submission.ts:112` — Regrade plus pending retry run concurrently, writing duplicate grades
  - Why: The status guard deliberately accepts 'grading' so stuck jobs can re-run — but that same acceptance lets an admin regrade (which re-enqueues) execute concurrently with a still-queued pg-boss retry of the original job: the worker runs GRADING_CONCURRENCY=5 parallel handlers, both jobs read status 'grading'/'submitted', both pass, and both commit the step-7 transaction. Grade has no unique(submissionId) constraint, so the student receives two 'grade is ready' notifications, CostLog double-counts the model spend, and two provisional Grade rows exist — the review queue and scoring then key off whichever createdAt is newest, which can differ from the one an instructor already opened.
  - Fix: Make the status flip a compare-and-set claim: `const claimed = await db.submission.updateMany({ where: { id, status: { in: ['submitted','grading'] } }, data: { status: 'grading' } })` is insufficient alone; instead guard the final transaction — inside step 7, re-check `submission.status !== 'graded'` (updateMany where status:'grading' and abort if count 0), or use pg-boss singletonKey = submissionId on send so only one job per submission is active at a time.
  - Reviewers: adversarial; confidence 75; validated true.

- safe-fetch/screenshot DNS-rebinding TOCTOU is a documented v1 trade-off, reachable from any student appUrl/portfolio link.

- Praxy export deep-scan inspects string values and keys but not numeric values under unlisted keys.
- CostLog has no index despite groupBy/orderBy reporting queries; no CI check guards migration/schema drift.
