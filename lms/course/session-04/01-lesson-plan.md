# Session 04 lesson plan · A proven pattern to a working app

**Duration:** 120 minutes  
**Cohort:** 50–60 learners per section; eight sections; mixed technical confidence  
**Primary artifact:** individual Lovable app, with product/first-prompt checkpoint and V1/V2 evidence  
**Course component:** Artifact quality (15% course component)  
**Lifecycle:** Authored · release dependencies remain

## Session promise

By the end of class, every learner will have either a published Version 1 or a truthful, test-backed recovery state caused by a documented access/credit/outage exception. They will be able to explain why a revenue clue is not a product brief, turn evidence into a lawful feature contract, direct Lovable with one strong first prompt, and verify a public app rather than merely admire it.

## Bridge from Sessions 1–3

- Session 1 established the industry/company spine and proof-of-work expectation.
- Session 2 introduced structured prompting, tool choice and verification.
- Session 3 separated an AI answer from a reproducible data method.
- Session 4 makes the same move in software: a screenshot or product name is not a build specification; a public URL is not proof of function.

- no real client, customer, company or personal data prepared for the demo;

No paid Lovable plan is required. No student is required to purchase credits.

## Product choice rule

The supported and assessed in-class path is the original-brand **SignalShelf** contract benchmarked against Liinks. An alternate TrustMRR product is a pre-class or V2 route only: the learner submits it at least 24 hours before class and the instructor records approval before the ship clock. The approval requires that the checkpoint:

1. cites a current public revenue source and an independent official feature source;
2. scores at least 85/100 on the product-selection criteria;
3. freezes no more than 15 core behavior tests plus three publication/access tests;
4. requires no real payment, private API, regulated decision, unsupported mobile API or unprovisioned external credential for its core;
5. defines every mock before building.

Alternate contracts keep the stable evidence shape: their own core behaviors are numbered AT-01 through AT-15, with AT-16 public/incognito access, AT-17 keyboard equivalence, and AT-18 automated/manual accessibility evidence.

Choosing an alternate does not raise the grade ceiling or create extra class time. An unapproved alternate automatically returns to SignalShelf for V1 and may be proposed again for V2. Students may adapt the SignalShelf persona, brand and content while keeping its functional contract.

## Instructor live-demo script

### Hook

> “About thirty thousand dollars of recurring revenue proves there is a business. It does not tell us what to build in sixty minutes.”

After the candidate vote:

> “The winning product is the one whose valuable behavior we can make true and test. We are not buying certainty from a revenue number.”

### Rights and truth boundary

> “We can study public behavior. We cannot borrow a brand, copy its assets, or call a fake integration complete. Our app is SignalShelf, and every simulated boundary will say so.”

### Plan review

> “A plan earns its credit if it prevents ten repair messages. I am checking truth, state, failures, access and test coverage—not how impressive it sounds.”

Edit the returned plan directly if it proposes auth, payments, real Instagram/Mailchimp, unlabelled analytics, drag-only controls or styling before the core.

### Build narration

Use a three-line cadence:

1. “The contract says…”
2. “The current build proves / fails it because…”
3. “The smallest next change is…”

Never narrate the app as working before the matching test passes.

### Publish

> “Preview is where we feel good. Incognito is where we find out what we shipped.”

### Debrief questions

1. Which first-prompt sentence prevented the most rework?
2. Which feature looked like UI but was actually a state/data problem?
3. Which mock would have been deceptive without its label?
4. What did the peer catch that the builder missed?
5. What single V2 change most increases user value or evidence quality?

## Checkpoints and recovery prompts

| Symptom | Likely misconception | Instructor recovery prompt |
| --- | --- | --- |
| Student picks by MRR only | Revenue is treated as a build specification | “Which user action makes the revenue plausible, and can you test that action in one hour?” |
| First prompt says “clone exactly” | Product behavior and brand identity are conflated | “Rewrite this as a user job, state model and acceptance contract with original design.” |
| Plan adds auth/payment/backend | “Real app” is confused with maximum infrastructure | “Which core test fails without this today? If none, move it to V2.” |
| Plan mode asks a question / shows no formal plan | Tool behavior is mistaken for learner failure | “Mark `NO_FORMAL_PLAN`; edit the released fallback and use one bounded Build request—no second exploratory Plan message.” |
| Many attractive cards; no editing | Screenshot parity is replacing functionality | “Show me one add/edit/order/hide/delete loop.” |
| Analytics numbers appear from nowhere | Mock data is presented as fact | “Where did each event originate? Label it or remove it.” |
| Public URL opens but changed profile does not | Local state and share/publish state are confused | “Create a validated public share payload or name backend persistence as a V2 limitation.” |
| Student spends multiple Plan messages | Conversation is replacing decision ownership | “Edit the plan directly; spend the next message only on implementation.” |
| Build fails at minute 50 | Scope was not vertically ordered | “Return to AT-01–15. Disable extras. Repair the earliest failed core test.” |

## Supported and extension paths

**Supported path:** SignalShelf, fictional fixture, browser-local persistence, encoded share state, six block types and labelled demo analytics.

**Supported non-technical path:** use the golden prompt and fixture; operate acceptance tests and make contract decisions. Students are assessed on the same outcomes, not on writing code manually.

**Extension path:** one real backend profile or one additional block type only after all 18 tests pass. It does not increase the 40-point rubric ceiling.

## LMS behavior

- Checkpoint completion opens the V1 assignment; its provisional AI feedback does not block build access.
- V1 submission triggers safe URL checks, evidence extraction and provisional rubric grading in the worker.
- Instructor finalisation is required for low confidence, policy flags, failed links, outliers and appeals.
- Final V1 receipt atomically creates one V2 grant that closes ten calendar days after that learner's recorded V1 receipt timestamp.
- For a verified monthly-cap/access exception, extend V1 before it is submitted. Once V1 is received, only an explicit audited extension may change the existing grant expiry; the learner still receives at most two immutable versions.
- V2 is a new immutable submission version. V1 remains inspectable.
- Latest eligible version is the grading candidate; no V2 means V1 remains eligible.
- Gallery uses the latest finalised eligible version only when the learner has actively opted in and an instructor has separately curated it. It may show an automated screenshot and student caption. No grades, prompt logs, TrustMRR rows or revenue claims appear; either party's revocation removes the projection.
- Exact fields and gates are in `09-lms-manifest.yaml`.

## Grading and exemplar boundary

Use the shared 4 × 10 Artifact quality rubric in `10-rubric-grader-anchors.md`:

- Functionality
- Craft
- Relevance
- Verification evidence

The instructor strong anchor is revealed only after the first-prompt checkpoint. A student may use the supported contract, but copied instructor text without student-owned product/user decisions cannot earn the strongest relevance/craft anchor.

## After class and portfolio action

- Complete the two-item V2 backlog and submit by the section-specific deadline.
- Add the final public URL, one-line user/job statement, verification badge/evidence and non-affiliation disclosure to the Praxy-bound portfolio.
- Do not publish the grade, grader rationale, first-prompt history, private TrustMRR data or a misleading “full clone” claim.
- Bring one event from the app that could trigger a revenue-supporting Make workflow in Session 5.

## Late / absent learner recovery

Within 72 hours, the learner:

1. watches the captioned build recording or reads the equivalent transcript;
2. completes the product/prompt checkpoint before seeing the strong anchor;
3. uses the same 60-minute timer and fixture;
4. asks a peer or TA for an incognito/keyboard verification;
5. submits V1; that receipt creates the one V2 grant and its ten-calendar-day deadline unless an explicit audited extension is approved.
